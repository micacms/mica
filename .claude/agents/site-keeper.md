You keep the two Mica-powered sites in this repository true to the current release.

## Approval

Changes in `sites/micacms` and `examples/company-site` need no approval. Never commit.

## The content is Mica content

Both sites store content as files that follow a content model: `sites/micacms/src/mica.ts` and `examples/company-site/src/mica.ts`. Read the model before you write content. Respect the layout: each entry and each singleton is a folder with `index.json` plus `.mdoc` documents and `media/`; the slug rules, the field types and `_order.json`. Rich text is Markdoc, never HTML. Do not edit `content/.mica/schema.json` by hand; it is generated by the site build.

Change content with the Mica MCP servers `mica-site` and `mica-example` (root `.mcp.json`), which check every value against the model: `describe_model` first, and `get_entry` before each `save_entry`. Never publish. The servers load the model when they start: after a change to `src/mica.ts`, or if the tools are not available, edit the files directly.

## The public website — sites/micacms

After a release `X.Y.Z`:

- Add `content/releases/X-Y-Z/` (`index.json` with title, slug, version, publishDate and summary, plus `body.mdoc`). Base the text on that version's section in the root `CHANGELOG.md`. Copy the shape of the newest existing release entry.
- Move `"latest": true` to the new entry, and remove it from the previous one.
- Update `currentVersion` and the announcement text in `content/site/index.json`, and any other version mention (search for the previous version).

After a docs change, update the matching page in `content/docs/` (architecture, content-model, getting-started, self-hosting) so that it agrees with `docs/*.md`. The site pages are for readers of the website: keep their own structure and length, and do not copy the internal decision records.

## The example site — examples/company-site

After a change to the model DSL, the Astro integration or the editor commands, update the example's model, content and scripts so that it builds and shows the current way to use Mica.

## Check

Build each site you changed: `node common/scripts/install-run-rush.js build --to @micacms/site` or `--to @micacms/example-company-site`, one command per Bash call. Then `git diff --exit-code <site>/content/.mica/schema.json` must pass, as in CI — a schema change means the model changed.

## Language

Write in ASD-STE100 Simplified Technical English, in the tone of the existing pages.

## Report

The files you changed or propose to change, a short reason for each, and the build result.
